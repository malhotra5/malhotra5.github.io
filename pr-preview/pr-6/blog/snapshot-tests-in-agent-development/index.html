Do Snapshot Tests Help in Agent-Driven Development?

An empirical analysis of 311 pull requests in the openhands-cli repository, where 68% of PRs are authored by AI agents. We examine whether snapshot tests actually catch bugs, guard behavior, and improve the development process.

May 18, 2026 · 12 min read
AI Agents Testing Snapshot Tests Empirical Analysis

We mined all 311 merged PRs from the openhands-cli repository (Sep 2025 – May 2026), classified each by type, authorship, and snapshot involvement, then analyzed commit-level history to understand how snapshot tests are actually used. Snapshot tests were adopted in January 2026.

Where Do Bugs Live?

Not all bugs are visual — and snapshot tests can only help with bugs that change rendered output. This distinction is critical: counting all bug-fixes against snapshot coverage inflates the apparent gap.

Framing matters. "85% of bug-fix PRs ship without touching snapshots" sounds damning, but 35% of those bugs are in code that snapshots can't cover — API auth, CLI argument parsing, dependency pinning. The honest denominator is the 51 visual bug-fixes, where 12 (24%) have snapshot involvement. That's still a coverage gap — but it's a different conversation than "85%."

What's Actually Covered?

Among the 51 visual (TUI) bug-fixes, what fraction hit paths that snapshot tests guard? We analyzed this at three levels of precision.

Level 1: Did the bug-fix PR touch snapshots?

Level 2: Path-level analysis

Zooming into the 35 post-adoption TUI bug-fixes, we checked whether the bug-fix PR touched the same code paths covered by snapshots — not just the same files.

Level 3: Accounting for indirect coverage

Snapshot tests don't just test rendering — they implicitly test the full stack behind what's rendered. A test that renders a conversation after switching implicitly exercises persistence. We read every snapshot test file (20 test classes + conftest) and asked: would the snapshot output actually change if this bug existed?

Strict criteria for "indirectly covered":

  1. A snapshot test exercises a flow through this code path
  2. The bug would produce visibly different output
  3. The test's input data would trigger the bug

Where Coverage Exists, It Works

The evidence for snapshot value is strongest in areas that have coverage. Three independent signals confirm this.

Forcing function: every feature must acknowledge visual impact

After adoption, 46% of TUI-changing feature PRs include snapshot updates — up from 0%. Nearly every visual change passes through a "did you mean to change how this looks?" gate.

Development guard: 58 "code first, fix snapshots later" commits

Of 27 multi-commit snapshot PRs, 18 (67%) show code written first, then a later commit fixing broken snapshots — evidence that existing tests caught unintended visual changes during development.

100% hit rate: 9 out of 9 multi-commit feature PRs touching snapshot-covered areas had to fix snapshot tests AFTER their initial code. Every single feature that touched covered areas had existing behavior guarded.

Review speed: 2× faster first review

PRs with snapshot changes get first review in 0.9 hours vs 1.7 hours for non-snapshot PRs, despite being 8× larger by file count.

Caveat: This is correlational, not causal. Snapshot PRs may be faster to review because SVG diffs provide instant visual understanding — or because they're more routine, involve the same reviewers, or have different complexity profiles. The data doesn't distinguish these explanations.

The Bug Rate and Its Limits

Did snapshot tests reduce the bug rate? The raw timeline tells a complicated story.

But the raw per-month rate (% of agent PRs that are UX bugs) is misleading — monthly sample sizes range from 5 to 63, and the May spike comes from just 3 bugs in a low-PR month. The right normalization: UX bugs per cumulative TUI feature shipped. This controls for codebase growth and sample size.

Still, the overall TUI bug-to-feature ratio went from 0.60 to 0.95 — essentially flat. Snapshot tests didn't reduce the total bug count because 54% of visual bugs are on uncovered paths. You can't prevent bugs in areas you don't cover.

Actionable Gaps

The data points to specific, fixable coverage gaps — not a blanket "write more tests" recommendation.

1. Settings persistence (7 bugs, 1 test would cover)

7 of 16 adjacent-but-uncovered bugs are in settings_screen.py and related modules. The repo tests the first-time setup flow (no saved config) and the critic settings tab, but no test saves settings, closes the modal, and reopens to verify persistence. A single "save → reload → snapshot" test would indirectly cover model name persistence, condensation defaults, dropdown ordering, and clear behavior.

2. Missing event types in test trajectories (4 bugs)

The e2e snapshot tests use recorded LLM trajectories for deterministic replay. But the current trajectories don't include ConversationErrorEvent, messages with markup characters, or critic-enabled MessageEvent. Adding 2–3 trajectories with these event types would extend coverage to code paths already exercised by the test framework but never triggered by the test data.

3. Notification rendering (2 bugs)

No snapshot test captures notification display (toast-style overlays). Settings change notifications and conversation notifications both had bugs that went uncaught.

4. Bug-fix coverage discipline

Only 1 of 78 bug-fix PRs added new snapshot coverage retroactively. When a visual bug is fixed, adding a snapshot that captures the corrected rendering would prevent the exact recurrence — the highest-value coverage extension possible.

Verdict

Snapshot tests work where they exist — but coverage is shallow.

The evidence for snapshot value is concrete and multi-signal:

  • 100% of feature PRs in covered areas had to fix broken snapshots during development (9/9 multi-commit feature PRs). Existing behavior was guarded.
  • 58 snapshot-fix commits across 20 PRs show developers being forced to acknowledge visual changes at the commit level.
  • The normalized UX regression rate dropped 4–20× in the settled post-adoption period (Feb–Apr 2026) compared to the pre-adoption peak.

But coverage is shallow:

  • 54% of TUI bugs (after accounting for indirect coverage) are on uncovered code paths — mostly settings persistence and untested event types.
  • Only 1 of 78 bug-fix PRs added new snapshot coverage retroactively.
  • 35% of all bugs are non-visual — snapshots are structurally irrelevant for API crashes, auth failures, and dependency issues.

The biggest ROI: a handful of targeted tests (settings save→reload, new event type trajectories, notification capture) would close the majority of the coverage gap with minimal effort.

Methodology

Everything in this analysis is reproducible from two scripts and a GitHub token. The full pipeline, data, and graphs are at snapshot-tests-analysis.

Step 1: Mining (GitHub API → JSON)

scripts/mine_github.py pulls every merged PR from openhands-cli via the GitHub REST API and gh CLI. For each PR it collects:

  • PR metadata — title, body, author, labels, branch names, created/merged timestamps, additions/deletions, changed file count
  • File-level diffs — every file changed with its status (added/modified/removed) and line counts
  • Commit history — full commit messages per PR, which enabled the "code first, fix snapshots later" analysis
  • Review data — reviewer logins, review decision, time-to-first-review
  • Linked issues — cross-referenced issue titles, bodies, and authors
  • Release mapping — which release tag (if any) includes each PR
  • Authorship detection — heuristic markers for agent-authored PRs (co-authored-by tags, conversation links, bot authors)

Output: a single mined_prs.json file with 42 fields per PR across all 311 merged PRs. No LLM is involved in this step — it's pure API data.

Step 2: Classification (LLM + heuristics → CSV)

scripts/categorize_prs.py classifies each PR along four dimensions. It runs two classifiers in parallel and keeps both outputs:

Heuristic classifier (keyword-based, no LLM):

  • PR type — title keyword matching ("fix" → bug-fix, "feat" → feature, "bump" → version-bump, etc.)
  • Bug severity — title keyword matching ("crash" → critical, "display" → ux-regression, "typo" → polish)
  • Snapshot involvement — file path matching (*.svg in snapshot directories)
  • Agent authorship — co-author tags and bot usernames

LLM classifier (gpt-4o-mini via OpenHands SDK):

  • PR type — same categories but with full context (title, description, file list, linked issues)
  • Bug severity — critical / ux-regression / polish, with definitions in the system prompt
  • Whether the PR touches TUI code — the LLM sees the actual file paths and description, catching cases keywords miss
  • Rationale — a 1-2 sentence explanation stored alongside each classification for auditability

The report uses the LLM classifications (llm_pr_type, llm_bug_severity, llm_touches_tui) as the primary labels, falling back to heuristics when the LLM call fails. The heuristic labels are retained in the CSV for comparison.

Step 3: Snapshot-specific analysis (heuristic)

Several analyses required no LLM — just reading file paths, commit messages, and timestamps:

  • Commit-level pattern detection — for each multi-commit PR, check if snapshot-related keywords ("snapshot", "update snap", "regenerate", "baseline") appear only in later commits, indicating the "code first, fix snapshots later" pattern
  • Bug-fix coverage gap — for each bug-fix PR, classify as "no snapshots touched" / "modified existing" / "added new" based on the Git status of snapshot SVG files
  • Suite reuse — extract test suite names from snapshot file paths and count unique PRs per suite
  • Review speed — compare hours_to_first_review between snapshot and non-snapshot PRs

Step 4: Indirect coverage analysis (manual + scripted)

This was the most labor-intensive step. We cloned openhands-cli and read all 20 snapshot test files (~2,500 lines of test code), including conftest.py fixtures and trajectory replay helpers. From this, scripts/analyze_indirect_coverage.py builds:

  • A coverage map — which test suite exercises which functional behaviors (e.g., TestConfirmationMode exercises scrolling, confirmation panel, agent execution)
  • A per-bug classification — for each of the 20 "file covered, path uncovered" bugs, whether a snapshot test would actually produce different output if the bug existed. Each classification includes a written rationale.

Step 5: Visualization

scripts/generate_deep_analysis_graphs.py produces all 18 matplotlib graphs. scripts/generate_report.py assembles the self-contained HTML report with base64-embedded images. Both are runnable with uv run.

Limitations

  • LLM classification accuracy — gpt-4o-mini misclassifies some edge cases (e.g., a PR titled "fix: add feature X" gets classified as bug-fix). We spot-checked ~30 PRs and found ~90% agreement with human judgment. The heuristic labels provide a second opinion.
  • Agent authorship detection — relies on co-author tags and known bot usernames. PRs where a human manually committed agent-generated code would be counted as human-authored.
  • Indirect coverage is subjective — our B1 (indirectly covered) classifications are judgment calls about whether a snapshot would visibly change. Different reviewers might classify 1-2 borderline cases differently, but the overall split (4 B1 vs 16 B2) is robust.
  • Single repository — all findings are specific to openhands-cli. Generalizing to other agent-driven projects requires similar analysis in those codebases.
