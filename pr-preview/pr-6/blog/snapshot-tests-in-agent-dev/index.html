Do Snapshot Tests Help in Agent-Driven Development?

An empirical analysis of 311 pull requests in the OpenHands-CLI repository to determine if snapshot tests improve the software development process when using Agents.

May 19, 2026 · 12 min read · Originally on Substack ↗
AI Agents Testing Snapshot Tests Empirical Analysis

Agents are now employed liberally in all parts of the software development cycle. They generate code and surrounding artifacts e.g. ticket descriptions, PR descriptions, documentation, Slack comments. Seemingly we’re developing applications faster than ever. In reality, we see neither experience increased velocity or improved product quality (see references in Appendix). The time saved is spent reviewing and verifying code, as agents frequently break things. So I’m in pursuit of finding improved ways to verify code such that using agents is safe for everyone.

Verification is an ambiguous and time consuming task

I hypothesized there are two problems with respect to verification:

  1. Determining intended behavior. We’re loosing a high quality source of truth as many tickets produced via agents are walls of text and often slightly inaccurate. Reviewers depend on the legitimacy of this, and also the agent itself for future iterations of work.
  2. Verifying implemented behavior. Manual quality assurance (QA) reveals problems, and is time consuming. With rapid heaps of code being generated this process doesn’t scale well.

I hypothesize that if application behavior is visually observable, and any change in existing behavior are obvious, we make it easier to verify changes and safer to use agents in future development efforts. A picture is worth a thousand words.

Analyzing whether visualizing application behavior improves verification

To test this hypothesis, I mined all 311 merged PRs from the OpenHands-CLI repository (Sep 2025 – May 2026), classified each by type, authorship, and snapshot involvement, then analyzed commit-level history to understand how snapshot tests are actually used. Snapshot tests were adopted in January 2026. For the anatomy of a snapshot test, see the Appendix.

68% of all PRs are agent authored. Percentage of agent-authored PRs over time are relatively consistent (excluding the second month), giving a reasonable baseline for investigating effects of snapshot tests.

Snapshots were introduced in January 2026, which were predominantly authored by agents. Not every PR includes snapshot changes, which we’ll explore is either due to behavioral changes that aren’t related to the UI or because of a lack of adding disciplined coverage to UI.

Where Do Bugs Live?

Not all bugs are visual. Snapshot tests helps with bugs that change rendered output. Counting all bug-fixes against snapshot coverage inflates the count.

The largest category is UI widgets & screens (38), where 12 PRs involved snapshot changes (green). But 27 bugs (35%) are entirely non-visual: CLI core, config/state, API/auth. Snapshot tests are structurally irrelevant for these.

Critical bugs skew non-visual (44%, crashes, auth failures, dependency issues). UX regressions are predominantly visual (75%), the natural domain for snapshot tests.

“85% of bug-fix PRs ship without touching snapshots” sounds damning, but 35% of those bugs are in code that snapshots can’t cover (API auth, CLI argument parsing, dependency pinning). The honest denominator is the 51 visual bug-fixes, where 12 (24%) have snapshot involvement. It’s still a big coverage gap, but it’s a different conversation than “85%.”

What’s Actually Covered?

Among the 51 visual (UI) bug-fixes, what fraction hit paths that snapshot tests guard? We analyzed this at three levels of precision.

Level 1: Did the bug-fix PR touch snapshots?

Of all 78 bug-fixes, 66 (85%) ship without touching snapshots. 11 (14%) modified existing baselines. Only 1 (1%) added new coverage.

Level 2: Path-level analysis

Zooming into the 35 post-adoption UI bug-fixes, we checked whether the bug-fix PR touched the same code paths covered by snapshots (not just the same files).

Level 3: Accounting for indirect coverage

Snapshot tests can be a proxy for application behavior. A test that renders a conversation after switching implicitly exercises persistence. We read every snapshot test file (20 test classes + conftest) and asked: would the snapshot output actually change if this bug existed?

Strict criteria for “indirectly covered”:

  1. A snapshot test exercises a flow through this code path
  2. The bug would produce visibly different output
  3. The test’s input data would trigger the bug

After accounting for indirect coverage: 46% of UI bugs hit covered paths (up from 34%). 4 bugs are indirectly covered. 16 (46%) remain in adjacent-but-uncovered paths. Revised: 46% covered, 54% uncovered.

Where Coverage Exists, It Works

The evidence for snapshot value is strongest in areas that have coverage.

Four independent signals confirm this.

Forcing function: every feature must acknowledge visual impact

Feature PRs (green) climb to 100% — every UI feature now passes through a “did you mean to change how this looks?” gate. Bug-fix PRs (red) plateau at ~35–50%. Since this graph is already filtered to UI (visual) bugs, the gap isn’t about non-visual code — it’s about coverage depth. Of the 34 post-adoption UI bug-fixes, 12 land on snapshot-covered paths and update the baseline to reflect the corrected behavior. The other 22 fix bugs on paths that have no snapshot tests at all (settings persistence, notifications, dropdown ordering), so there’s no baseline to update.

Snapshots break during development — and the signal is acted on

Across 27 multi-commit snapshot PRs, 18 (67%) show a pattern: code written first, then a later commit addressing broken snapshots — 58 snapshot-fix commits total. Developers hit snapshot failures during development and iterate before pushing.

Feature PRs generated the most (24 snapshot-fix commits across 9 PRs). Refactors generated 11 — code restructuring that wasn’t intended to change visual output was caught doing exactly that.

How do snapshot failures ultimately resolve?

Of the 128 PRs with snapshot CI data (late Jan–mid May 2026), 29 (23%) triggered at least one snapshot failure. When a snapshot fails, the developer has two choices: update the baseline (acknowledging an intentional visual change) or fix their code (reverting an unintended regression).

To classify each of these 29 PRs, we checked whether the failing test’s snapshot file was updated in the final merged PR (baseline update) or left unchanged (code fix). GitHub retains CI logs for ~90 days, so we could only verify the specific failing test names for the 9 most recent PRs (March–May 2026). For the remaining 20, we fall back to a coarser heuristic: whether the merged PR contains any snapshot file changes at all.

The breakdown by type makes the pattern intuitive:

  • CI and docs PRs are entirely blue — these PRs shouldn’t change visual output, so every failure was a regression caught.
  • Dependency bumps are mostly blue — an upstream change broke the UI, and snapshots caught it.
  • Features split 50/50 — half intentionally changed the UI (baseline updated), half accidentally broke something else (code fixed).
  • Version bumps and bug fixes are entirely green — version strings and bug-fix behavior changes are expected visual updates.

Overall, 11 of 29 PRs (38%) fixed their code rather than updating baselines — concrete regressions prevented from shipping. Snapshot tests were advisory (not a required check) during part of this period, and 3 PRs merged with failures still present.

Review speed: 2× faster first review

PRs with snapshot changes get first review in 0.9 hours vs 1.7 hours for non-snapshot PRs, despite being 8× larger by file count.

Caveat: This is correlational, not causal. Snapshot PRs may be faster to review because SVG diffs provide instant visual understanding, or because they’re more routine, involve the same reviewers, or have different complexity profiles. The data doesn’t distinguish these explanations.

The Bug Rate and Its Limits

Did snapshot tests reduce the bug rate? The raw timeline tells a complicated story.

Critical bugs (red) drop to zero by March 2026. UX regressions (orange) spike in the adoption month, settle through Feb–Apr, then spike again in May. At face value, UX regressions got worse.

But the raw per-month rate (% of agent PRs that are UX bugs) is misleading — monthly sample sizes range from 5 to 63, and the May spike comes from just 3 bugs in a low-PR month. The right normalization: UX bugs per cumulative UI feature shipped. This controls for codebase growth and sample size.

Normalized view: UX bugs per cumulative UI feature. Pre-adoption peaked at 0.45. The adoption month (Jan 2026) started at 0.44 — same level, coinciding with a huge feature push. The settled post-adoption rate (Feb–Apr) drops to 0.02–0.10, which is 4–20× lower. The May spike barely registers when normalized against the growing feature base.

Still, the overall UI bug-to-feature ratio went from 0.60 to 0.95. Essentially flat. Snapshot tests didn’t reduce the total bug count because 54% of visual bugs are on uncovered paths. You can’t prevent bugs in areas you don’t cover.

Investigating testing gaps to supplement bug rates

The data points to specific, fixable coverage gaps not a blanket “write more tests” recommendation.

1. Settings persistence (7 bugs, 1 test would cover)

7 of 16 adjacent-but-uncovered bugs are in settings_screen.py and related modules. The repo tests the first-time setup flow (no saved config) and the critic settings tab, but no test saves settings, closes the modal, and reopens to verify persistence. A single “save → reload → snapshot” test would indirectly cover model name persistence, condensation defaults, dropdown ordering, and clear behavior.

2. Missing event types in test trajectories (4 bugs)

The e2e snapshot tests use recorded LLM trajectories for deterministic replay. But the current trajectories don’t include ConversationErrorEvent, messages with markup characters, or critic-enabled MessageEvent. Adding 2–3 trajectories with these event types would extend coverage to code paths already exercised by the test framework but never triggered by the test data.

3. Notification rendering (2 bugs)

No snapshot test captures notification display (toast-style overlays). Settings change notifications and conversation notifications both had bugs that went uncaught.

4. Bug-fix coverage discipline

Only 1 of 78 bug-fix PRs added new snapshot coverage retroactively. When a visual bug is fixed, adding a snapshot that captures the corrected rendering would prevent the exact recurrence — the highest-value coverage extension possible.

Verdict

Snapshot tests work where they exist — but coverage is shallow.

The evidence for snapshot value is concrete and multi-signal:

  • 100% of feature PRs in covered areas had to fix broken snapshots during development (9/9 multi-commit feature PRs). Existing behavior was guarded.
  • 58 snapshot-fix commits across 20 PRs show developers being forced to acknowledge visual changes at the commit level.
  • The normalized UX regression rate dropped 4–20× in the settled post-adoption period (Feb–Apr 2026) compared to the pre-adoption peak.

But coverage is shallow:

  • 54% of UI bugs (after accounting for indirect coverage) are on uncovered code paths — mostly settings persistence and untested event types.
  • Only 1 of 78 bug-fix PRs added new snapshot coverage retroactively.
  • 35% of all bugs are non-visual — snapshots are structurally irrelevant for API crashes, auth failures, and dependency issues.

The biggest ROI: a handful of targeted tests (settings save→reload, new event type trajectories, notification capture) would close the majority of the coverage gap with minimal effort.

Methodology

The full pipeline, data, and graphs are reproducible from snapshot-tests-analysis.

Mining

We pulled every merged PR from OpenHands-CLI via the GitHub REST API: PR metadata, file-level diffs, full commit history, review data, linked issues, and authorship signals (co-author tags, bot usernames). This produced 311 PRs with 42 fields each. No LLM involved.

For CI analysis, we queried the Check Runs API for every commit in every post-adoption PR to extract the “Run snapshot tests” result. For the 29 PRs that triggered failures, we downloaded CI job logs (where still available — GitHub retains these ~90 days), parsed out specific failing test names, and cross-referenced each against the files changed in the final merged PR to determine whether resolution was a code fix or baseline update.

Classification

Each PR was classified by type, bug severity, snapshot involvement, and whether it touches UI code. We ran two classifiers in parallel:

  1. Keyword heuristics — title pattern matching (“fix” → bug-fix, “feat” → feature, etc.) and file path matching for snapshot involvement.
  2. LLM (gpt-4o-mini) — given the PR title, description, file list, and linked issues, outputs a JSON classification with rationale. The prompt:
Given a PR's title, description, file list, and linked issues,
output a JSON object with:
{
  "pr_type": one of "bug-fix", "feature", "refactor", "test",
             "ci", "docs", "dependency-bump", "version-bump", "other",
  "bug_severity": one of "critical", "ux-regression", "polish",
  "touches_ui": true/false,
  "rationale": "1-2 sentence explanation"
}

We did not formally validate LLM accuracy against human labels for this study. Classification of PR types from structured metadata is a well-characterized task for modern LLMs, and prior work shows strong agreement with human judgment on similar labeling problems. Keyword heuristics are retained alongside LLM labels for comparison.

Indirect coverage analysis

We read all 20 snapshot test files (~2,500 lines) to build a coverage map of which test suites exercise which functional behaviors. For each of the 20 “file covered, path uncovered” bugs, we assessed whether a snapshot test would actually produce different output if the bug existed.

Limitations

  • Agent authorship detection — relies on co-author tags and bot usernames. PRs where a human manually committed agent-generated code would be counted as human-authored.
  • CI log expiry — only 9 of 29 failing PRs had logs available for test-level verification. The remaining 20 use a coarser heuristic (whether the merged PR contains any snapshot file changes), which can’t distinguish updating the failing test’s baseline from updating a different test’s baseline.
  • Indirect coverage is subjective — different reviewers might classify 1-2 borderline cases differently, but the overall split (4 indirectly covered vs 16 uncovered) is robust.
  • Single repository — all findings are specific to OpenHands-CLI.

Appendix

Anatomy of a snapshot

The OpenHands-CLI is built using Textual, a Python library for building terminal UIs. Textual has excellent support for snapshot testing, rendering widgets to SVG and comparing them across runs. The codebases uses two types of snapshots

  1. Component snapshots: capture standalone rendering of individual components, sometimes under different configurations.
  2. Behavior snapshots: iteratively capture a sequence of snapshots over time during interactive flows, effectively emulating a short video.

Once snapshots are committed to the repository, they become part of the system history. Future pull requests automatically check against them. If behavior changes, the snapshot test fails. The failure is visually obvious, showing exactly how the behavior differs from the expected output.

They are cheap to maintain, and in this specific scenario are not flaky. Agents do well generating these tests.

Example Snapshot Test

import pytest
from textual.pilot import Pilot
from .helpers import type_text, wait_for_app_ready, wait_for_idle
from openhands.sdk.security.confirmation_policy import NeverConfirm
from openhands_cli.tui.textual_app import OpenHandsApp


class TestEchoHelloWorld:
    """Test echo hello world conversation."""

    # Specify pre-seed LLM responses trajectory
    @pytest.mark.parametrize(
        "mock_llm_with_trajectory",
        ["simple_echo_hello_world"],
        indirect=True,
    )
    def test_echo_hello_world_conversation(
        self,
        snap_compare,
        mock_llm_with_trajectory,
    ):
        async def run_conversation(pilot: Pilot):
            """Simulate user typing and submitting a command."""
            await wait_for_app_ready(pilot)
            await type_text(pilot, "echo hello world")
            await pilot.press("enter")
            await wait_for_idle(pilot)

        # Use fixed conversation ID from fixture
        # for deterministic snapshots
        app = OpenHandsApp(
            exit_confirmation=False,
            initial_confirmation_policy=NeverConfirm(),
            resume_conversation_id=mock_llm_with_trajectory[
                "conversation_id"
            ],
        )

        # Run simulation + take snapshot
        assert snap_compare(
            app,
            terminal_size=(120, 40),
            run_before=run_conversation,
        )

Limitations of Snapshot Testing

It is difficult to generalize this exact approach to every codebase. Not all systems have easily visualizable behavior, and not all frameworks support snapshot testing as naturally as Textual. Snapshots can become expensive to run as more tests accumulate. They cannot capture animations, as those are hard to capture at precise moments and create flaky tests as a consequence. They work best when relying less on external services.
