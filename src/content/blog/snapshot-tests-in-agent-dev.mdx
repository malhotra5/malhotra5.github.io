Agents are now employed liberally in all parts of the software development cycle. They generate code and surrounding artifacts e.g. ticket descriptions, PR descriptions, documentation, Slack comments. Seemingly we're developing applications faster than ever. In reality, we see neither experience increased velocity or improved product quality. The time saved is spent reviewing and verifying code, as agents frequently break things. Thus, I'm in a pursuit of finding improved ways to verify code that makes agents safe to use for everyone.

## Verification is an ambiguous and time consuming task

I hypothesized there are two problems with respect to verification:

1. **Determining intended behavior.** Where is the source of truth for how the product should behave? If an agent details application behavior in a ticket description, is it accurate? The agent user needs to spend time determining whether the task was captured properly. Are the contributor and reviewer actually aligned on the intended behavior? Reviewers depend on the legitimacy of this, and so does the agent itself during future iterations of work.&#x20;
2. **Verifying implemented behavior.** Once the code has been implemented, how can we easily verify that the application implements the intended behavior? Manually running and validating the application reveals new problems. It's time-consuming and doesn't scale well when agents are producing large volumes of code.

I hypothesize that if application behavior is visually observable, and any change in existing behavior are obvious, we make it **easier to verify changes and safer to use agents in future development efforts.**

To test this hypothesis, I [mined](#step-1-mining-github-api--json) all 311 merged PRs from the [Openhands-CLI](https://github.com/OpenHands/openhands-cli) repository (Sep 2025 – May 2026), [classified](#step-2-classification-llm--heuristics--csv) each by type, authorship, and snapshot involvement, then analyzed [commit-level history](#step-3-snapshot-specific-analysis-heuristic) to understand *how* snapshot tests are actually used. Snapshot tests were adopted in January 2026. For the anatomy of a snapshot test, see the [Appendix](#appendix-snapshot-testing-in-the-openhands-cli).

68% of all PRs are agent authored. Percentage of agent-authored PRs over time are relatively consistent (excluding the second month), giving a reasonable baseline for investigating effects of snapshot tests.&#x20;

Snapshots were introduced in January 2026, which were predominantly authored by agents. Not every PR includes snapshot changes, which we'll explore is either due to behavioral changes that aren't related to the UI or because of a lack of adding disciplined coverage to UI.

### Where Do Bugs Live?

Not all bugs are visual. Snapshot tests helps with bugs that change rendered output. Counting all bug-fixes against snapshot coverage inflates the count.

<Figure src="/img/snapshot-analysis/deep_16_bugfix_domain.png" alt="Bug-fix PRs categorized for visual vs non-visual fixes" caption="Bug-fix PRs categorized for visual vs non-visual fixes" />

The largest category is TUI widgets & screens (38), where 12 PRs involved snapshot changes (green). But 27 bugs (35%) are entirely non-visual: CLI core, config/state, API/auth. Snapshot tests are structurally irrelevant for these.

<Figure src="/img/snapshot-analysis/deep_17_severity_by_domain.png" alt="Severity breakdown for bug types" caption="Severity breakdown for bug types" />

Critical bugs skew non-visual (44%, crashes, auth failures, dependency issues). UX regressions are predominantly visual (75%), the natural domain for snapshot tests.

> **"85% of bug-fix PRs ship without touching snapshots"** sounds damning, but 35% of those bugs are in code that snapshots *can't* cover (API auth, CLI argument parsing, dependency pinning). The honest denominator is the 51 visual bug-fixes, where 12 (24%) have snapshot involvement. It's still a big coverage gap, but it's a different conversation than "85%."

### What's Actually Covered?

Among the 51 visual (TUI) bug-fixes, what fraction hit paths that snapshot tests guard?
We analyzed this at three levels of precision.

#### Level 1: Did the bug-fix PR touch snapshots?

<Figure src="/img/snapshot-analysis/deep_13_bugfix_coverage_gap.png" alt="PR-level coverage gap" caption="PR-level coverage gap" />

Of all 78 bug-fixes, 66 (85%) ship without touching snapshots. 11 (14%) modified existing baselines. Only 1 (1%) added new coverage.

#### Level 2: Path-level analysis

Zooming into the 35 post-adoption TUI bug-fixes, we checked whether the bug-fix PR touched
the same code *paths* covered by snapshots (not just the same files).

<Figure src="/img/snapshot-analysis/deep_15_covered_vs_uncovered.png" alt="Path-level coverage breakdown" caption="Path-level coverage breakdown" />

#### Level 3: Accounting for indirect coverage

Snapshot tests can be a proxy for application behavior. A test that renders a conversation after switching implicitly exercises persistence. We [read every snapshot test file](#step-4-indirect-coverage-analysis-manual--scripted) (20 test classes + conftest) and asked: *would the snapshot output actually change if this bug existed?*

Strict criteria for "indirectly covered":

1. A snapshot test exercises a flow through this code path
2. The bug would produce **visibly different** output
3. The test's input data would trigger the bug

<Figure src="/img/snapshot-analysis/deep_18_reclassified_coverage.png" alt="Reclassified path-level coverage" caption="Reclassified path-level coverage" />

After accounting for indirect coverage: 46% of TUI bugs hit covered paths (up from 34%). 4 bugs are indirectly covered. 16 (46%) remain in adjacent-but-uncovered paths. Revised: 46% covered, 54% uncovered.

## Where Coverage Exists, It Works

The evidence for snapshot value is strongest in areas that have coverage.
Four independent signals confirm this.

### Forcing function: every feature must acknowledge visual impact

<Figure src="/img/snapshot-analysis/deep_4_forcing_function.png" alt="Percentage of feature and bug-fix PRs that include snapshot changes, by month." caption="Percentage of feature and bug-fix PRs that include snapshot changes, by month." />

Feature PRs (green) climb to 100% — every TUI feature now passes through a "did you mean to change how this looks?" gate. Bug-fix PRs (red) plateau at ~35–50%. Since this graph is already filtered to TUI (visual) bugs, the gap isn't about non-visual code — it's about coverage depth. Of the 34 post-adoption TUI bug-fixes, 12 land on snapshot-covered paths and update the baseline to reflect the corrected behavior. The other 22 fix bugs on paths that have no snapshot tests at all (settings persistence, notifications, dropdown ordering), so there's no baseline to update.

### Snapshot CI: what happens when tests fail?

We mined the "Run snapshot tests" check-run result for every commit in every post-adoption PR. The snapshot CI workflow was added in late January 2026, so the first 67 PRs (all from early–mid January) predate it. Of the **128 PRs with snapshot CI data** (late Jan–mid May 2026), **29 (23%)** triggered at least one snapshot failure during development.

<Figure src="/img/snapshot-analysis/deep_19_ci_outcomes.png" alt="Left: 128 PRs with snapshot CI, 29 triggered failures. Right: breakdown showing 14 baseline only, 10 code fixed, 2 both, 3 merged with failure." caption="Snapshot CI outcomes across 128 post-adoption PRs. Counts are adjusted using test-level data where CI logs were available." />

Of those 29 failures:

- **14 (48%) updated baselines only** — the visual change was intentional and acknowledged. (CI logs expired for these PRs, so we can't verify at the test level.)
- **10 (34%) fixed their code** — the snapshot caught an unintended change and the developer fixed the code to match the existing baseline.
- **2 (7%) did both** — fixed code for the failing tests (regressions caught) *and* updated baselines for other tests (intentional changes). The PR-level view would have classified these as pure "baseline updates," hiding the regression catch.
- **3 (10%) merged with CI still failing** — snapshot tests were advisory (not a required check) during part of the adoption period. These PRs ([#595](https://github.com/OpenHands/openhands-cli/pull/595), [#698](https://github.com/OpenHands/openhands-cli/pull/698), [#699](https://github.com/OpenHands/openhands-cli/pull/699)) bypassed the signal.

The "both" category comes from a test-level cross-reference. GitHub retains CI job logs for ~90 days. For the **9 most recent PRs with failures** (March–May 2026), we downloaded the logs, extracted the specific failing test names, and checked whether each failing test's snapshot directory was actually modified in the final PR. Every failing test across all 9 PRs was resolved by a code fix. Two of those PRs (#719, #715) also updated baselines — but for *different* tests than the ones that were failing.

<Figure src="/img/snapshot-analysis/deep_21_test_level_vs_pr_level.png" alt="Per-PR bar chart of failing snapshot tests. All bars are blue (code fixed). PRs #715 and #719 are highlighted as also updating baselines for other tests." caption="How failing snapshot tests were actually resolved (5 PRs with parseable CI logs, March–May 2026). Purple labels mark PRs that also updated baselines for other (non-failing) tests." />

We can't verify the 14 "baseline only" PRs at the test level (logs expired). But the pattern in our sample is clear: the PR-level view missed regressions caught in 2 of 5 verifiable PRs. The real regression-catch rate is at minimum **41%** (12 of 29) and likely higher if the same pattern holds for the unverifiable PRs.

### Development pattern: code first, fix snapshots later

CI is only the final check. At the commit level, developers hit snapshot failures earlier and iterate before pushing.

<Figure src="/img/snapshot-analysis/deep_14_snapshot_guarding.png" alt="Snapshot-fix commits by PR type (later-in-PR commits only)." caption="Snapshot-fix commits by PR type (later-in-PR commits only)." />

Across 27 multi-commit snapshot PRs, **18 (67%)** show code written first, then a later commit addressing broken snapshots — 58 snapshot-fix commits total. Feature PRs generated the most (24 across 9 PRs). Refactors generated 11 — code restructuring that wasn't intended to change visual output was caught doing exactly that.

### Review speed: 2× faster first review

PRs with snapshot changes get first review in **0.9 hours** vs
**1.7 hours** for non-snapshot PRs, despite being 8× larger by file count.

<Figure src="/img/snapshot-analysis/deep_6_review_speed.png" alt="Review speed comparison" caption="Snapshot PRs get first review ~2× faster." />

**Caveat:** This is correlational, not causal. Snapshot PRs may be faster to review because SVG diffs provide instant visual understanding, or because they're more routine, involve the same reviewers, or have different complexity profiles. The data doesn't distinguish these explanations.

## The Bug Rate and Its Limits

Did snapshot tests reduce the bug rate? The raw timeline tells a complicated story.

<Figure src="/img/snapshot-analysis/5_bug_rate_timeline.png" alt="Critical vs UX regression bug rate over time" caption="Critical and UX regression bug rate over time" />

Critical bugs (red) drop to zero by March 2026. UX regressions (orange) spike in the adoption month, settle through Feb–Apr, then spike again in May. At face value, UX regressions got worse.

But the raw per-month rate (% of agent PRs that are UX bugs) is misleading — monthly
sample sizes range from 5 to 63, and the May spike comes from just 3 bugs in a
low-PR month. The right normalization: UX bugs per cumulative TUI feature shipped.
This controls for codebase growth and sample size.

<Figure src="/img/snapshot-analysis/deep_10_bug_rate_with_context.png" alt="Normalized UX regression rate" caption="Normalized UX regression rate" />

Normalized view: UX bugs per cumulative TUI feature. Pre-adoption peaked at 0.45. The adoption month (Jan 2026) started at 0.44 — same level, coinciding with a huge feature push. The settled post-adoption rate (Feb–Apr) drops to 0.02–0.10, which is 4–20× lower. The May spike barely registers when normalized against the growing feature base.

Still, the overall TUI bug-to-feature ratio went from **0.60 to 0.95**. Essentially flat. Snapshot tests didn't reduce the total bug count because 54% of visual bugs are on uncovered paths. You can't prevent bugs in areas you don't cover.

## Investigating testing gaps to supplement bug rates&#x20;

The data points to specific, fixable coverage gaps not a blanket "write more tests" recommendation.

### 1. Settings persistence (7 bugs, 1 test would cover)

7 of 16 adjacent-but-uncovered bugs are in `settings_screen.py` and related modules.
The repo tests the *first-time setup flow* (no saved config) and the
*critic settings tab*, but no test saves settings, closes the modal, and reopens to
verify persistence. A single "save → reload → snapshot" test would indirectly cover model
name persistence, condensation defaults, dropdown ordering, and clear behavior.

### 2. Missing event types in test trajectories (4 bugs)

The e2e snapshot tests use recorded LLM trajectories for deterministic replay. But the current
trajectories don't include `ConversationErrorEvent`, messages with markup
characters, or critic-enabled `MessageEvent`. Adding 2–3 trajectories with these
event types would extend coverage to code paths already exercised by the test framework but
never triggered by the test data.

### 3. Notification rendering (2 bugs)

No snapshot test captures notification display (toast-style overlays). Settings change
notifications and conversation notifications both had bugs that went uncaught.

### 4. Bug-fix coverage discipline

Only 1 of 78 bug-fix PRs added new snapshot coverage retroactively.
When a visual bug is fixed, adding a snapshot that captures the corrected rendering
would prevent the exact recurrence — the highest-value coverage extension possible.

## Verdict

**Snapshot tests work where they exist — but coverage is shallow.**

The evidence for snapshot value is concrete and multi-signal:

* **100% of feature PRs** in covered areas had to fix broken snapshots during development (9/9 multi-commit feature PRs). Existing behavior was guarded.
* **58 snapshot-fix commits** across 20 PRs show developers being forced to acknowledge visual changes at the commit level.
* The **normalized UX regression rate dropped 4–20×** in the settled post-adoption period (Feb–Apr 2026) compared to the pre-adoption peak.

But coverage is shallow:

* **54% of TUI bugs** (after accounting for indirect coverage) are on uncovered code paths — mostly settings persistence and untested event types.
* **Only 1 of 78 bug-fix PRs** added new snapshot coverage retroactively.
* **35% of all bugs are non-visual** — snapshots are structurally irrelevant for API crashes, auth failures, and dependency issues.

The biggest ROI: a handful of targeted tests (settings save→reload, new event type
trajectories, notification capture) would close the majority of the coverage gap with
minimal effort.

## Methodology

Everything in this analysis is reproducible from two scripts and a GitHub token.
The full pipeline, data, and graphs are at
[snapshot-tests-analysis](https://github.com/malhotra5/snapshot-tests-analysis).

### Step 1: Mining (GitHub API → JSON)

`scripts/mine_github.py` pulls every merged PR from
[openhands-cli](https://github.com/OpenHands/openhands-cli)
via the GitHub REST API and `gh` CLI. For each PR it collects:

* **PR metadata** — title, body, author, labels, branch names, created/merged timestamps, additions/deletions, changed file count
* **File-level diffs** — every file changed with its status (added/modified/removed) and line counts
* **Commit history** — full commit messages per PR, which enabled the "code first, fix snapshots later" analysis
* **Review data** — reviewer logins, review decision, time-to-first-review
* **Linked issues** — cross-referenced issue titles, bodies, and authors
* **Release mapping** — which release tag (if any) includes each PR
* **Authorship detection** — heuristic markers for agent-authored PRs (co-authored-by tags, conversation links, bot authors)

Output: a single `mined_prs.json` file with 42 fields per PR across all 311 merged PRs.
No LLM is involved in this step — it's pure API data.

### Step 2: Classification (LLM + heuristics → CSV)

`scripts/categorize_prs.py` classifies each PR along four dimensions.
It runs two classifiers in parallel and keeps both outputs:

**Heuristic classifier** (keyword-based, no LLM):

* PR type — title keyword matching ("fix" → bug-fix, "feat" → feature, "bump" → version-bump, etc.)
* Bug severity — title keyword matching ("crash" → critical, "display" → ux-regression, "typo" → polish)
* Snapshot involvement — file path matching (`*.svg` in `snapshot` directories)
* Agent authorship — co-author tags and bot usernames

**LLM classifier** (gpt-4o-mini via [OpenHands SDK](https://docs.openhands.dev/sdk)):

* PR type — same categories but with full context (title, description, file list, linked issues)
* Bug severity — critical / ux-regression / polish, with definitions in the system prompt
* Whether the PR touches TUI code — the LLM sees the actual file paths and description, catching cases keywords miss
* Rationale — a 1-2 sentence explanation stored alongside each classification for auditability

The report uses the LLM classifications (`llm_pr_type`, `llm_bug_severity`,
`llm_touches_tui`) as the primary labels, falling back to heuristics when the LLM
call fails. The heuristic labels are retained in the CSV for comparison.

### Step 3: Snapshot-specific analysis (heuristic)

Several analyses required no LLM — just reading file paths, commit messages, and timestamps:

* **Commit-level pattern detection** — for each multi-commit PR, check if snapshot-related keywords ("snapshot", "update snap", "regenerate", "baseline") appear only in later commits, indicating the "code first, fix snapshots later" pattern
* **Bug-fix coverage gap** — for each bug-fix PR, classify as "no snapshots touched" / "modified existing" / "added new" based on the Git status of snapshot SVG files
* **Suite reuse** — extract test suite names from snapshot file paths and count unique PRs per suite
* **Review speed** — compare `hours_to_first_review` between snapshot and non-snapshot PRs

### Step 4: Indirect coverage analysis (manual + scripted)

This was the most labor-intensive step. We cloned openhands-cli and read all 20 snapshot test
files (\~2,500 lines of test code), including `conftest.py` fixtures and trajectory
replay helpers. From this, `scripts/analyze_indirect_coverage.py` builds:

* A **coverage map** — which test suite exercises which functional behaviors (e.g., `TestConfirmationMode` exercises scrolling, confirmation panel, agent execution)
* A **per-bug classification** — for each of the 20 "file covered, path uncovered" bugs, whether a snapshot test would *actually produce different output* if the bug existed. Each classification includes a written rationale.

### Step 5: Visualization

`scripts/generate_deep_analysis_graphs.py` produces all 18 matplotlib graphs.
`scripts/generate_report.py` assembles the self-contained HTML report with
base64-embedded images. Both are runnable with `uv run`.

### Limitations

* **LLM classification accuracy** — gpt-4o-mini misclassifies some edge cases (e.g., a PR titled "fix: add feature X" gets classified as bug-fix). We spot-checked \~30 PRs and found \~90% agreement with human judgment. The heuristic labels provide a second opinion.
* **Agent authorship detection** — relies on co-author tags and known bot usernames. PRs where a human manually committed agent-generated code would be counted as human-authored.
* **Indirect coverage is subjective** — our B1 (indirectly covered) classifications are judgment calls about whether a snapshot would visibly change. Different reviewers might classify 1-2 borderline cases differently, but the overall split (4 B1 vs 16 B2) is robust.
* **Single repository** — all findings are specific to openhands-cli. Generalizing to other agent-driven projects requires similar analysis in those codebases.

## Appendix: Snapshot Testing in the OpenHands CLI

I experimented with snapshot testing in the
[OpenHands command-line interface (CLI)](https://github.com/OpenHands/openhands-cli)
codebase. The CLI is built using
[Textual](https://textual.textualize.io/),
a Python library for building terminal UIs. One advantage of Textual is that it provides
excellent support for snapshot testing — rendering widgets to SVG and comparing them
across runs.

### Two Kinds of Snapshots

Snapshots were used in two ways:

#### 1. Component Snapshots

We capture standalone renders of individual components. These snapshots allow us to
verify that specific UI components render correctly in isolation. If a change alters
the output, the snapshot test fails and shows the difference.

#### 2. Behavioral Snapshots

We also capture a sequence of snapshots over time, effectively emulating a short video of
the application's behavior. This allows us to test interactive flows — for example:

1. Start the CLI
2. Send a message
3. Observe the agent response
4. Watch the UI update

The sequence of frames becomes a behavioral recording of the feature.

### Why Snapshots Help

A picture is worth a thousand words. Snapshots allow:

* **Authors** to confirm that their change behaves correctly
* **Reviewers** to understand the behavior quickly
* **Agents** to validate whether their outputs changed the system

Once snapshots are committed to the repository, they become part of the system history.
Future pull requests automatically check against them. If behavior changes, the snapshot
test fails. The failure is visually obvious, showing exactly how the behavior differs
from the expected output.

They are cheap to maintain, and in this specific scenario are not flaky. Agents do well
generating these tests.

### Example Snapshot Test

```python
import pytest
from textual.pilot import Pilot
from .helpers import type_text, wait_for_app_ready, wait_for_idle
from openhands.sdk.security.confirmation_policy import NeverConfirm
from openhands_cli.tui.textual_app import OpenHandsApp


class TestEchoHelloWorld:
    """Test echo hello world conversation."""

    # Specify pre-seed LLM responses trajectory
    @pytest.mark.parametrize(
        "mock_llm_with_trajectory",
        ["simple_echo_hello_world"],
        indirect=True,
    )
    def test_echo_hello_world_conversation(
        self,
        snap_compare,
        mock_llm_with_trajectory,
    ):
        async def run_conversation(pilot: Pilot):
            """Simulate user typing and submitting a command."""
            await wait_for_app_ready(pilot)
            await type_text(pilot, "echo hello world")
            await pilot.press("enter")
            await wait_for_idle(pilot)

        # Use fixed conversation ID from fixture
        # for deterministic snapshots
        app = OpenHandsApp(
            exit_confirmation=False,
            initial_confirmation_policy=NeverConfirm(),
            resume_conversation_id=mock_llm_with_trajectory[
                "conversation_id"
            ],
        )

        # Run simulation + take snapshot
        assert snap_compare(
            app,
            terminal_size=(120, 40),
            run_before=run_conversation,
        )
```

### Limitations of Snapshot Testing

It is difficult to generalize this exact approach to every codebase. Not all systems have
easily visualizable behavior, and not all frameworks support snapshot testing as naturally
as Textual. Snapshots can become expensive to run as more tests accumulate. They cannot
capture animations, as those are hard to capture at precise moments and create flaky tests
as a consequence. They work best when relying less on external services.

### Lessons Learned

The specific tooling may vary across projects, but the underlying principle seems broadly
useful. To make codebases more compatible with autonomous agents, we likely need two properties:

1. **Behavior should be easy to visualize**
2. **Behavioral changes should fail in obvious and reliable ways**

When these conditions are met, both humans and agents gain a much clearer signal about
whether the system behaves as intended.
