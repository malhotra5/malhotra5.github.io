Agents are now employed liberally in all parts of the software development cycle. They generate code and surrounding artifacts e.g. ticket descriptions, PR descriptions, documentation, Slack comments. Seemingly we're developing applications faster than ever. In reality, we see neither experience increased velocity or improved product quality (see references in Appendix). The time saved is spent reviewing and verifying code, as agents frequently break things. So I'm in pursuit of finding improved ways to verify code such that using agents is safe for everyone.

## Verification is an ambiguous and time consuming task

I hypothesized there are two problems with respect to verification:

1. **What is the application supposed to do?** Agent-generated tickets and PR descriptions are a summary of everything; sometimes inaccurate or outdated. Reviewers depend on this as the source of truth, and so does the agent itself during future iterations.&#x20;
2. **Did the code actually do it?** Manual QA reveals problems but is time consuming. With the volume of code agents generate, it doesn't scale.

Snapshot tests, I hypothesize, address both problems with the same mechanism. If application behavior is visually observable, and any change in existing behavior are obvious, we make it **\*\*easier to verify changes and safer to use agents in future development efforts.\*\***  [A picture is worth a thousand words](https://en.wikipedia.org/wiki/A_picture_is_worth_a_thousand_words).

## The Dataset

To test this hypothesis, I [mined](#mining) all 311 merged PRs from the [OpenHands-CLI](https://github.com/OpenHands/openhands-cli) repository (Sep 2025 – May 2026), [classified](#classification) each by type, authorship, and snapshot involvement, then analyzed commit-level history to understand *how* snapshot tests are actually used. Snapshot tests were adopted in January 2026. For the anatomy of a snapshot test, see the [Appendix](#appendix).

### Snapshots break during development, indicating changes in behavior

Out of 311 PRs, we have 128 post snapshot adoption PRs with CI data. **29 (15%)** triggered at least one snapshot failure.

Bug-fix and feature PRs generated the most failure events (11 and 10 respectively). We're most interested in features, refactors, and bug fixes. The other categorizes are more routine changes.&#x20;

### How do snapshot failures ultimately resolve?

When a snapshot fails, the developer has two choices: update the baseline (acknowledging an intentional visual change) or fix their code (reverting an unintended regression). We classified each PR's resolution using CI logs where available and file-change heuristics for the rest (see [Methodology](#mining) for details).

<Figure src="/img/snapshot-analysis/deep_19_ci_outcomes.png" alt="Stacked bar chart showing how 29 PRs with snapshot failures resolved, by type. Features: 4 baseline, 4 code fix. CI/Docs: 5 code fix. Bug fix: 3 baseline, 1 merged. Dep bump: 1 baseline, 2 code fix. Refactor: 2 baseline, 1 merged. Version bump: 3 baseline. Test: 2 baseline, 1 merged." caption="How 29 PRs with snapshot failures resolved, broken down by PR type. Green = updated baseline (intentional change). Blue = fixed code (regression caught). Red = merged with CI still failing." />

The breakdown by type makes the pattern intuitive:

* **CI and docs PRs**: these PRs shouldn't change visual output, so every failure was a regression caught.
* **Dependency bumps**: an upstream change broke the UI, and snapshots caught it. Some required legitimate baseline updates though.
* **Features**: Half intentionally changed the UI, half accidentally broke something else.
* **Version bumps:** the application renders its version in the UI, so these&#x20;
* Bugs: and bug-fix behavior changes are expected visual updates.

Overall, **11 of 29 PRs (38%)** fixed their code, due to a regression, rather than updating baselines. For the PRs which merged with failing CI, snapshot tests were advisory (not a required check) during part of this period.

### Review speed: 2× faster first review

PRs with snapshot changes get first review in **0.9 hours** vs
**1.7 hours** for non-snapshot PRs, despite being 8× larger by file count.

<Figure src="/img/snapshot-analysis/deep_6_review_speed.png" alt="Review speed comparison" caption="Snapshot PRs get first review ~2× faster." />

This is correlational, not causal. Snapshot PRs may be faster to review because SVG diffs provide instant visual understanding, or because they're more routine, involve the same reviewers, or have different complexity profiles. The data doesn't distinguish these explanations.

## But Coverage Is Shallow

The evidence above comes from areas where snapshots exist. How much of the codebase do they actually cover?

### The bug rate

Did snapshot tests reduce the bug rate? The raw timeline tells a complicated story.

<Figure src="/img/snapshot-analysis/5_bug_rate_timeline.png" alt="Critical vs UX regression bug rate over time" caption="Critical and UX regression bug rate over time" />

Critical bugs (red) drop to zero by March 2026. UX regressions (orange) spike in the adoption month, settle through Feb–Apr, then spike again in May. At face value, UX regressions got worse.

But the raw per-month rate (% of agent PRs that are UX bugs) is misleading — monthly
sample sizes range from 5 to 63, and the May spike comes from just 3 bugs in a
low-PR month. The right normalization: UX bugs per cumulative UI feature shipped.
This controls for codebase growth and sample size.

<Figure src="/img/snapshot-analysis/deep_10_bug_rate_with_context.png" alt="Normalized UX regression rate" caption="Normalized UX regression rate" />

Normalized view: UX bugs per cumulative UI feature. Pre-adoption peaked at 0.45. The adoption month (Jan 2026) started at 0.44 — same level, coinciding with a huge feature push. The settled post-adoption rate (Feb–Apr) drops to 0.02–0.10, which is 4–20× lower. The May spike barely registers when normalized against the growing feature base.

Still, the overall UI bug-to-feature ratio went from **0.60 to 0.95**. Essentially flat. Snapshot tests didn't reduce the total bug count because the majority of visual bugs are on uncovered paths. You can't prevent bugs in areas you don't cover.

### Where do bugs live?

Not all bugs are visual. Snapshot tests help with bugs that change rendered output. Counting all bug-fixes against snapshot coverage inflates the count.

<Figure src="/img/snapshot-analysis/deep_16_bugfix_domain.png" alt="Bug-fix PRs categorized for visual vs non-visual fixes" caption="UI widgets & screens is the largest category (38 bugs), but 27 bugs (35%) are entirely non-visual — CLI core, config/state, API/auth — where snapshots are structurally irrelevant." />

<Figure src="/img/snapshot-analysis/deep_17_severity_by_domain.png" alt="Severity breakdown for bug types" caption="Critical bugs skew non-visual (44% — crashes, auth failures, dependency issues). UX regressions are predominantly visual (75%), the natural domain for snapshot tests." />

85% of bug-fix PRs ship without touching snapshots, but 35% of those bugs are in code that snapshots *can't* cover (API auth, CLI argument parsing, dependency pinning). The relevant denominator is the 51 visual bug-fixes, where 12 (24%) have snapshot involvement. That's still a coverage gap, but a different one than the headline number suggests.

### What's actually covered?

Among the 51 visual (UI) bug-fixes, what fraction hit paths that snapshot tests guard?

#### Level 2: Path-level analysis

Zooming into the 35 post-adoption UI bug-fixes, we checked whether the bug-fix PR touched
the same code *paths* covered by snapshots (not just the same files).

<Figure src="/img/snapshot-analysis/deep_15_covered_vs_uncovered.png" alt="Path-level coverage breakdown" caption="Most post-adoption UI bugs land on paths where snapshot files exist but the specific bug path is uncovered (orange)." />

#### Level 3: Accounting for indirect coverage

Snapshot tests can be a proxy for application behavior. A test that renders a conversation after switching implicitly exercises persistence. We [read every snapshot test file](#indirect-coverage-analysis) (20 test classes + conftest) and asked: *would the snapshot output actually change if this bug existed?*

Strict criteria for "indirectly covered":

1. A snapshot test exercises a flow through this code path
2. The bug would produce **visibly different** output
3. The test's input data would trigger the bug

After accounting for indirect coverage: 46% of UI bugs hit covered paths (up from 34%). 4 bugs are indirectly covered — a snapshot test exercises a flow through the bug's code path but wasn't originally counted because the PR didn't modify snapshot files. 16 (46%) remain in adjacent-but-uncovered paths.

## Investigating testing gaps to supplement bug rates

The data points to specific, fixable coverage gaps not a blanket "write more tests" recommendation.

### 1. Settings persistence (7 bugs, 1 test would cover)

7 of 16 adjacent-but-uncovered bugs are in `settings_screen.py` and related modules.
The repo tests the *first-time setup flow* (no saved config) and the
*critic settings tab*, but no test saves settings, closes the modal, and reopens to
verify persistence. A single "save → reload → snapshot" test would indirectly cover model
name persistence, condensation defaults, dropdown ordering, and clear behavior.

### 2. Missing event types in test trajectories (4 bugs)

The e2e snapshot tests use recorded LLM trajectories for deterministic replay. But the current
trajectories don't include `ConversationErrorEvent`, messages with markup
characters, or critic-enabled `MessageEvent`. Adding 2–3 trajectories with these
event types would extend coverage to code paths already exercised by the test framework but
never triggered by the test data.

### 3. Notification rendering (2 bugs)

No snapshot test captures notification display (toast-style overlays). Settings change
notifications and conversation notifications both had bugs that went uncaught.

### 4. Bug-fix coverage discipline

Only 1 of 78 bug-fix PRs added new snapshot coverage retroactively.
When a visual bug is fixed, adding a snapshot that captures the corrected rendering
would prevent the exact recurrence — the highest-value coverage extension possible.

## Verdict

**Snapshot tests work where they exist — but coverage is shallow.**

On the [source of truth problem](#verification-is-an-ambiguous-and-time-consuming-task): where snapshots existed, committed baselines replaced prose as the definition of "what the application does." Feature PRs couldn't ship without explicitly showing their visual impact — the snapshot diff *is* the specification, not a ticket description. This made behavior concrete and reviewable at a glance.

On the [verification problem](#verification-is-an-ambiguous-and-time-consuming-task): snapshots automated the question "did the code break anything?" Developers iterated on broken snapshots during development, CI caught regressions, and the UX regression rate dropped meaningfully in the post-adoption period. The verification loop became visual and immediate rather than manual and ambiguous.

But coverage remained shallow. More than half of visual bugs landed on code paths with no snapshot tests at all, and almost no bug-fix PRs added new coverage retroactively. A significant portion of all bugs are non-visual entirely — API crashes, auth failures, dependency issues — where snapshots are structurally irrelevant.

A handful of targeted tests (settings save→reload, new event type trajectories, notification capture) would close the majority of the visual coverage gap.

### Caveats

This analysis primarily measures software quality, quantified in retrospect by the number of bugs patched. That's a lagging indicator — it tells us about regressions that *shipped*, not regressions that were *prevented* before merge or time saved during review. We don't measure developer velocity or review effort directly.

It also covers a single repository with a specific architecture (a Textual-based terminal UI with first-class SVG snapshot support). Several factors limit generalizability:

* **Framework dependency.** Textual's snapshot support is unusually clean — deterministic renders, no flakiness, cheap to run. Most UI frameworks don't offer this out of the box, and the cost-benefit calculus may differ significantly where snapshot infrastructure requires more effort.
* **Small team, high agent usage.** OpenHands-CLI has a small number of contributors with \~68% agent-authored PRs. The forcing-function effect may be stronger (or weaker) in teams with different human/agent ratios or review cultures.
* **Confounding factors.** Snapshot adoption coincided with a period of active feature development and team process maturation. We can't fully disentangle the effect of snapshots from other improvements happening in parallel (better test infrastructure, more experienced contributors, stabilizing codebase). The normalized regression rate drop is suggestive, not causal.
* **Survivorship bias in CI data.** We only analyzed merged PRs. PRs that were abandoned or reworked heavily due to snapshot failures — potentially the strongest evidence of snapshots preventing bad changes — are invisible in this dataset.

## Methodology

The full pipeline, data, and graphs are reproducible from [snapshot-tests-analysis](https://github.com/malhotra5/snapshot-tests-analysis).

### Mining

We pulled every merged PR from [OpenHands-CLI](https://github.com/OpenHands/openhands-cli) via the GitHub REST API: PR metadata, file-level diffs, full commit history, review data, linked issues, and authorship signals (co-author tags, bot usernames). This produced 311 PRs with 42 fields each. No LLM involved.

For CI analysis, we queried the Check Runs API for every commit in every post-adoption PR to extract the "Run snapshot tests" result. For the 29 PRs that triggered failures, we downloaded CI job logs (where still available — GitHub retains these \~90 days), parsed out specific failing test names, and cross-referenced each against the files changed in the final merged PR to determine whether resolution was a code fix or baseline update.

### Classification

Each PR was classified by type, bug severity, snapshot involvement, and whether it touches UI code. We ran two classifiers in parallel:

1. **Keyword heuristics** — title pattern matching ("fix" → bug-fix, "feat" → feature, etc.) and file path matching for snapshot involvement.
2. **LLM** (gpt-4o-mini) — given the PR title, description, file list, and linked issues, outputs a JSON classification with rationale. The prompt:

```
Given a PR's title, description, file list, and linked issues,
output a JSON object with:
{
  "pr_type": one of "bug-fix", "feature", "refactor", "test",
             "ci", "docs", "dependency-bump", "version-bump", "other",
  "bug_severity": one of "critical", "ux-regression", "polish",
  "touches_ui": true/false,
  "rationale": "1-2 sentence explanation"
}
```

We did not formally validate LLM accuracy against human labels for this study. Classification of PR types from structured metadata is a well-characterized task for modern LLMs, and prior work shows strong agreement with human judgment on similar labeling problems. Keyword heuristics are retained alongside LLM labels for comparison.

### Indirect coverage analysis

We read all 20 snapshot test files (\~2,500 lines) to build a coverage map of which test suites exercise which functional behaviors. For each of the 20 "file covered, path uncovered" bugs, we assessed whether a snapshot test would *actually produce different output* if the bug existed.

### Limitations

* **Agent authorship detection** — relies on co-author tags and bot usernames. PRs where a human manually committed agent-generated code would be counted as human-authored.
* **CI log expiry** — only 9 of 29 failing PRs had logs available for test-level verification. The remaining 20 use a coarser heuristic (whether the merged PR contains any snapshot file changes), which can't distinguish updating the *failing* test's baseline from updating a different test's baseline.
* **Indirect coverage is subjective** — different reviewers might classify 1-2 borderline cases differently, but the overall split (4 indirectly covered vs 16 uncovered) is robust.
* **Single repository** — all findings are specific to [OpenHands-CLI](https://github.com/OpenHands/openhands-cli).

## Appendix

### Anatomy of a snapshot

The [OpenHands-CLI](https://github.com/OpenHands/openhands-cli) is built using [Textual](https://textual.textualize.io/), a Python library for building terminal UIs. Textual has excellent support for snapshot testing, rendering widgets to SVG and comparing them across runs. The codebases uses two types of snapshots

1. **Component snapshots**: capture standalone rendering of individual components, sometimes under different configurations.
2. **Behavior snapshots**: iteratively capture a sequence of snapshots over time during interactive flows, effectively emulating a short video.

Once snapshots are committed to the repository, they become part of the system history. Future pull requests automatically check against them. If behavior changes, the snapshot test fails. The failure is visually obvious, showing exactly how the behavior differs from the expected output.

They are cheap to maintain, and in this specific scenario are not flaky. Agents do well
generating these tests.

### Example Snapshot Test

```python
import pytest
from textual.pilot import Pilot
from .helpers import type_text, wait_for_app_ready, wait_for_idle
from openhands.sdk.security.confirmation_policy import NeverConfirm
from openhands_cli.tui.textual_app import OpenHandsApp


class TestEchoHelloWorld:
    """Test echo hello world conversation."""

    # Specify pre-seed LLM responses trajectory
    @pytest.mark.parametrize(
        "mock_llm_with_trajectory",
        ["simple_echo_hello_world"],
        indirect=True,
    )
    def test_echo_hello_world_conversation(
        self,
        snap_compare,
        mock_llm_with_trajectory,
    ):
        async def run_conversation(pilot: Pilot):
            """Simulate user typing and submitting a command."""
            await wait_for_app_ready(pilot)
            await type_text(pilot, "echo hello world")
            await pilot.press("enter")
            await wait_for_idle(pilot)

        # Use fixed conversation ID from fixture
        # for deterministic snapshots
        app = OpenHandsApp(
            exit_confirmation=False,
            initial_confirmation_policy=NeverConfirm(),
            resume_conversation_id=mock_llm_with_trajectory[
                "conversation_id"
            ],
        )

        # Run simulation + take snapshot
        assert snap_compare(
            app,
            terminal_size=(120, 40),
            run_before=run_conversation,
        )
```

### Limitations of Snapshot Testing

It is difficult to generalize this exact approach to every codebase. Not all systems have
easily visualizable behavior, and not all frameworks support snapshot testing as naturally
as Textual. Snapshots can become expensive to run as more tests accumulate. They cannot
capture animations, as those are hard to capture at precise moments and create flaky tests
as a consequence. They work best when relying less on external services.
